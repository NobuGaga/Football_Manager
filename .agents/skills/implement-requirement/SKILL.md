# 实现需求

将用户消息中“实现需求”之后的内容，或显式调用本技能时随附的参数，作为本次需要实现的具体需求。完整执行实现、验证、GitHub 提交与推送、微信小程序测试版发布，不把只给方案或只修改代码视为完成。

如果没有提供具体需求，只请求用户补充需求，不修改文件，不提交，也不发布。

## 1. 理解与实现

1. 在仓库根目录工作，先阅读 `AGENTS.md`、`README.md`，并按其中的文档路由读取与需求有关的现行规则、工程文档、源码和测试；进入子目录前检查该处是否有更具体的 `AGENTS.md`。
2. 先检查 `git status --short` 和当前分支，区分已有改动与本次改动。保留用户已有工作，不覆盖、不删除、不 stash，也不把无关改动纳入提交。
3. 按具体需求完成全部相关实现，遵循项目现有结构、命名、依赖和测试约定。需求涉及业务行为时遵守现行规则；涉及文档已描述的命令、架构或行为时同步更新对应文档。
4. 不伪造数据、赛果、预测、凭证或发布结果，不绕过微信或 GitHub 的权限与安全限制，不执行公开审核或正式发布。

## 2. 验证

1. 运行项目现有且覆盖本次改动的标准测试、构建和必要的端到端验证，不能只检查导入或编译。Python 相关改动至少运行 `python3 -m unittest discover -s tests -v`；其他子项目使用各自已有的标准命令。
2. 无论需求是否修改小程序，发布前都在 `miniprogram/` 运行 `npm test`。依赖缺失时先按锁文件执行 `npm ci`；不得用绕过失败检查的方式继续发布。
3. 检查最终差异，修正本次改动造成的失败和过时文档。不要顺手修复无关问题。测试失败或需求仍只实现了一部分时，不提交、不推送、不发布。
4. 清理本次验证产生且不需要交付的临时文件、日志和测试输出，保留用户原有文件。

## 3. 提交并推送 GitHub

1. 只暂存本次需求涉及的文件，明确排除无关改动、凭证、私钥、`.env`、`project.private.config.json`、缓存、快照、锁文件、`node_modules/`、预览二维码和其他本地产物。
2. 审查暂存区，确认范围与敏感信息安全后，用概括本次需求的简洁提交信息创建 Git commit。不得使用 `git add -A` 或 `git add .`。
3. 将当前分支推送到其已配置的 GitHub 上游分支。使用现有 Git 凭证，不把令牌写入命令、远程 URL、文件或日志。推送被拒绝或发生冲突时保留现场并明确报告，不强推、不自动覆盖，也不擅自处理无关工作区改动。
4. 记录最终 commit 哈希和推送结果。没有确认推送成功时，不继续发布。

## 4. 发布最新微信小程序测试版

1. 这里的“测试版”指通过 `miniprogram-ci` 上传开发版本，并由默认 `CI 机器人 1` 持续更新的体验版；预览二维码、公开审核和正式发布均不能代替此步骤。
2. 确认 `miniprogram/` 中没有未提交或未跟踪的交付源码改动，确保上传内容就是刚推送的版本。若仍存在会进入上传包的未提交改动，停止发布并报告，不上传混合版本。
3. 确认运行环境已配置 `WECHAT_APPID` 和 `WECHAT_PRIVATE_KEY`，但不要输出、读取到回复中或写入仓库。保持默认 `CI 机器人 1` 和脚本自动生成的新版本号，不随意更换机器人或复用旧版本。
4. 在 `miniprogram/` 执行 `npm run upload`。上传失败时明确报告错误阶段，不宣称发布成功，也不改用预览二维码冒充体验版。
5. 只有命令成功后才报告最新版本号和发布结果。如果该机器人尚未绑定体验版，明确说明还需管理员在微信公众平台完成一次性“设为体验版”操作，不得把仅上传开发版本表述为体验版已更新。

## 5. 最终回复

用中文简要列出：

- 已实现的需求和关键改动；
- 实际运行的验证及结果；
- GitHub commit 哈希、分支和推送结果；
- 小程序版本号、上传结果及体验版状态；
- 尚未解决的阻塞或需要人工完成的事项。

任何一步未完成都要如实说明，不把部分完成表述为全部完成。
