# Football Manager 项目工程文档

更新日期：2026-11-08

实现范围：每日概率分析、Claw 定时推送与微信小程序报告快照。

## 1. 项目定位

对外名称统一为“足球经理的推断”，正文简称“推断”。现有 `predict` 命令、`predictions` 表与 `predicted_at` 等技术标识继续沿用；每日报告使用 `足球经理的推断_YYYY-MM-DD.*` 文件名，中文导入与导出首选“比赛编号”，导入仍兼容旧列名。历史报告、原始快照和归档文档保留原貌。

本项目是 Python 命令行批处理系统，不是网页应用，也不依赖 MCP。核心边界如下：

- **体彩官方对阵**决定“分析哪些比赛”；手动 CSV／JSON／Excel 导入是稳定主路径。
- **本地赛前文件与项目 AI 策略文档**提供预测输入和分类，不调用外部足球数据 API。
- **SQLite**保存原始快照、名称映射、赛前特征、推断版本、赛果与模型信息。
- **Poisson／Dixon–Coles 基线**输出概率而非确定结论。
- **Kimi**读取每日 JSON／CSV／Excel／Markdown 报告并生成批量分析。
- **赛后回测**评价概率质量、比分命中和校准，不以单次命中代替长期表现。

├── src/
│   ├── automation.py             # Git 安全、每日编排、锁和中文摘要
│   ├── miniprogram_export.py     # 每日报告到小程序数据的紧凑导出

│   ├── importers.py              # 对阵、映射、特征、赛果导入

│   ├── reporter.py               # 每日报告与回测 Excel
│   ├── result_checker.py         # 逐条推断赛果核对
│   ├── backtest.py               # Log Loss、Brier、校准、比分与 xG 误差

运行时目录：`data/football.db`、`data/snapshots/`、`data/cache/` 和 `reports/`。原始输入文件复制到快照目录，规范化内容同时保存在数据库中。

## 4. 数据流程

```text
官方对阵文件／可降级网页
  → 字段校验、时区转换、fixture_key 关联
  → fixtures + fixture_snapshots + 原始文件
  → team_aliases／match_review_queue
  → match_features（as_of 不晚于推断和开赛）
  → model_versions + predictions（追加式）
  → 每日 JSON／CSV／Excel／Markdown
  → results + result_checker
  → Backtester（总体及分联赛指标、概率校准）
```

对阵更新会保存新快照并更新当前视图，旧快照不变。比赛延期、取消通过 `match_status` 标记；推断默认排除 `cancelled`、`postponed`、`finished`。如果开赛时间改变但编号、当地日期和双方不变，仍关联同一 `fixture_key`。

## 5. 数据表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `fixtures` | `fixture_key`、编号、`business_date`、实际开赛日、联赛、双方、UTC 时间、时区、状态、赔率、外部 ID | 当前对阵视图 |
| `fixture_snapshots` | 获取时间、来源、内容哈希、原始 JSON、原始文件 | 不可变每日／临场快照 |
| `team_aliases` | 体彩名、标准名、英文名、provider、外部 ID、确认状态 | 跨数据源名称映射 |
| `match_features` | `as_of`、来源、特征 JSON、完整度、缺失项 | 时间截面赛前数据 |
| `predictions` | 三向概率、双方预期进球、比分分布、风险、模型版本、生成时间 | 追加式初版／临场推断 |
| `results` | 实际比分、赛果、录入时间、来源、复盘备注 | 赛后结果 |
| `model_versions` | 参数、训练区间、创建时间、回测结果 | 模型可复现性 |
| `match_review_queue` | 原因、候选、状态 | 无法唯一匹配时人工确认 |

旧 `matches` 表保留。迁移只复制可验证的对阵和赛果；旧推断缺少概率及推断时间，因此保留原表但不写入新版概率回测。

## 6. 输入数据约定

### 6.1 官方对阵

支持中文列名和英文列名，核心列为：`比赛编号`、`比赛日期`、`联赛`、`主队`、`客队`（或 `对阵`）、`开赛时间`、`执行时区`、`让球`、`销售状态`、`比赛状态`、六项赔率、`原始数据来源`。

- `比赛日期`／`business_date` 是体彩营业日；`match_date` 是按执行时区计算的实际开赛日。每日推断、报告、赛前补充和赛果同步统一按营业日筛选。
- 日期时间优先使用完整 `YYYY-MM-DD HH:MM`；只有 `MM-DD HH:MM` 时必须提供 `--date`。
- naive 时间按 `执行时区`解释，数据库统一保存 UTC，同时保留原时区用于报告和跨日判断。旧库迁移时以原 `match_date` 回填 `business_date`，不改动历史开赛时间。
- 未识别字段不会用“当前时间”“主队”“客队”等伪值补齐。

### 6.2 球队映射

列为 `alias／体彩名称`、`standard_name／标准名称`、`english_name／英文名称`、`league`、`provider`、`external_id`、`review_status`。外部比赛自动匹配综合使用双方映射和两小时开赛时间容差，不只依赖中文名；非唯一候选进入人工队列。

### 6.3 赛前特征

可用 `fixture_key` 关联，也可用编号、双方和日期唯一关联。`as_of` 是防止未来数据泄漏的必填语义字段。支持：

- `expected_home_goals`、`expected_away_goals`：明确预期进球，优先级最高；
- `home_xg`、`home_xga`、`away_xg`、`away_xga`；
- `home_attack`、`home_defense`、`away_attack`、`away_defense`：相对联赛均值的乘数；
- `injuries`、`lineups`、`recent_form`、`h2h`、双方休息天数等文字或结构化依据；
- 其他字段可放入 `features_json`，原样保留用于后续模型扩展。

## 7. 模型口径

当前版本为 `poisson-dc-v1`。预期进球按以下优先级估计：

1. 明确输入双方预期进球；
2. 主队 `(home_xg + away_xga) / 2`，客队 `(away_xg + home_xga) / 2`；
3. 联赛均值 × 攻防乘数；
4. 仅有完整胜平负赔率时，去除水位后作赔率降级估计，并写入风险标记；
5. 无任何数据时使用联赛基线均值，完整度很低，不应输出强结论。

基础比分概率为：

```text
P(H=h, A=a) = Poisson(h; λ_home) × Poisson(a; λ_away)
```

对 `0:0`、`0:1`、`1:0`、`1:1` 使用 Dixon–Coles `rho` 修正，再在 `0..10` 球网格上归一化。三向概率由完整比分矩阵求和，比分报告取前 5 项。模型参数保存在 `model_versions`，推断保存输入截止时间，便于复现。

这是一套可运行基线，不宣称已完成分联赛参数训练。升班马、小样本、杯赛、伤停与阵容不确定信息应通过特征和风险标记体现；后续可在滚动窗口中拟合分联赛参数并新增模型版本。

## 8. 报告与回测

每日报告每场包含基本信息、当地开赛时间、数据完整度和来源、三向概率、双方预期进球、前 5 比分及概率、分析依据、风险提示、模型版本、推断时间、赛后比分与复盘字段。

回测只使用已落库且满足以下条件的记录：

```text
input_as_of <= predicted_at <= start_time_utc
```

指标包括 Log Loss、三分类 Brier 分数、胜平负准确率、首选／前三准确比分命中率、双方预期进球平均绝对误差，以及按推断概率分箱的实际频率。总体和分联赛分别统计。这里的回测是**已保存推断的滚动赛后评价**，不是使用未来赛果重新训练后再评价同一批比赛。

## 9. 自动任务与运行边界

- GitHub 仅承担当前项目的版本管理，保存源码、文档和数据产物；仓库不配置或运行 GitHub Actions。
- Kimi Claw 是唯一的每日定时任务入口，负责运行命令、读取结果、生成中文预测策略并推送到聊天频道。
- `src/automation.py` 统一执行 Git 拉取、本地赛果文件、今日对阵、AI 策略推断、回测、中文运行摘要以及数据产物提交和推送。
- 单元测试和构建检查由开发者或 Claw 在本地运行，不依赖远端 CI，也不上传数据库或报告 artifact。
- 抓取失败不会静默继续。无人值守环境若官方网页不稳定，应在仓库外准备好对阵文件后改用手动导入命令。
- 项目不调用外部足球数据 API。赛前特征仅从本地文件读取，赛果仅从本地赛果文件回填；未提供文件时明确保留警告。
- `src/ai_strategies.py` 加载 `rules/strategies/` 中的 Markdown 和 JSON 分类配置，每次预测保存 AI 分类、策略 ID 和文档哈希。

## 11. Kimi Claw 每日自动化与策略推送

`scripts/daily_automation.sh` 是 Claw 定时任务的推荐命令入口，`python3 main.py daily` 是对应 Python 命令。执行顺序为：

```text
非并发锁与 Git 工作区检查
  → 可选 git pull --rebase
  → 初始化／迁移数据库
  → 本地文件回填昨日赛果
  → 核对已有推断
  → 文件或公开网页导入今日官方对阵
  → 读取本地赛前文件和所选 rules/strategies/<AI_MODEL>.md
  → 生成带 AI 分类的推断和四格式报告
  → 导出 miniprogram/data/daily-report.js
  → 生成回测 JSON 和中文运行摘要
  → 暂存 data/football.db、reports/ 与小程序每日数据
  → commit 并 push
  → scripts/wechat_daily_upload.sh 运行小程序测试并上传体验版
  → Claw 读取当日 JSON、运行状态和回测结果
  → 按现行策略规则生成中文预测策略并推送聊天频道
```

安全约束：

- 开始拉取或推送前要求工作区干净，避免覆盖人工修改。
- 文件锁防止 cron 重入；同一统计模型、AI 模型和策略 ID 下，非 refresh 不重复生成推断；不同 AI 分类可分别追加。
- 任何对阵或赛果关联错误都会中止后续推送；本地特征不足时保留风险并使用已有数据。
- 不把 token、API key 或频道 secret 写入仓库、摘要和长期记忆；`git push` 使用已配置的凭证，不在命令参数中拼接 token。
- `DAILY_NO_GIT=1` 用于手动验收，只生成和检查数据，不上传小程序；先验证摘要和提交范围，再按 `AGENTS.md` 配置非整点 cron。
- 正式任务默认上传小程序；`DAILY_MINIPROGRAM_UPLOAD=0` 可显式关闭。缺少微信凭证或 Node.js 时上传步骤显式失败，不能报告为体验版已更新。
- `reports/每日运行状态_日期.json` 供程序检查，`reports/足球经理的推断_日期.json` 是逐场策略和小程序打包的数据源，`reports/每日中文摘要_日期.md` 提供运行统计。只有每日命令、Git 推送和默认小程序上传均成功后，Claw 才生成并发送当日策略。

## 12. 微信小程序每日数据与运行边界

`src/miniprogram_export.py` 只导出页面需要的字段：比赛标识、双方、当地开赛时间、三向概率、预期进球、前两个比分、数据完整度、方法、风险、模型版本和推断时间；不把完整比分矩阵或数据库放入小程序。输出是 `miniprogram/data/daily-report.js`，每日页面从概览进入，展示打包时的报告快照。

`scripts/wechat_daily_upload.sh` 先运行页面和 CI 配置测试，再调用 `miniprogram/scripts/upload-ci.cjs`。上传备注包含报告日期；`preview-ci.cjs` 仍用于独立预览。两者由 Claw 在本地运行环境调用，不使用 GitHub Actions。上传凭证通过 `WECHAT_APPID`、`WECHAT_PRIVATE_KEY` 注入，私钥文件只在临时目录短暂存在；上传默认固定使用 CI 机器人 1，首次在公众平台绑定后，后续同机器人上传持续更新体验版。预览二维码写入本地指定路径，不作为仓库 artifact 上传。
