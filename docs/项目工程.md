## 1. 项目定位

本项目是 Python 命令行批处理系统，不是网页应用，也不依赖 MCP。核心边界如下：

- **体彩官方对阵**决定“分析哪些比赛”；手动 CSV／JSON／Excel 导入是稳定主路径。
- **专业足球数据源**只负责补充赛前数据；API-Football 为可选适配器。
- **SQLite**保存原始快照、名称映射、赛前特征、预测版本、赛果与模型信息。
- **Poisson／Dixon–Coles 基线**输出概率而非确定结论。
- **Kimi**读取每日 JSON／CSV／Excel／Markdown 报告并生成批量分析。
- **赛后回测**评价概率质量、比分命中和校准，不以单次命中代替长期表现。

## 4. 数据流程

```text
官方对阵文件／可降级网页
  → 字段校验、时区转换、fixture_key 关联
  → fixtures + fixture_snapshots + 原始文件
  → team_aliases／match_review_queue
  → match_features（as_of 不晚于预测和开赛）
  → model_versions + predictions（追加式）
  → 每日 JSON／CSV／Excel／Markdown
  → results + result_checker
  → Backtester（总体及分联赛指标、概率校准）
```

对阵更新会保存新快照并更新当前视图，旧快照不变。比赛延期、取消通过 `match_status` 标记；预测默认排除 `cancelled`、`postponed`、`finished`。如果开赛时间改变但编号、当地日期和双方不变，仍关联同一 `fixture_key`。

## 5. 数据表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `fixtures` | `fixture_key`、编号、联赛、双方、UTC 时间、时区、状态、赔率、外部 ID | 当前对阵视图 |
| `fixture_snapshots` | 获取时间、来源、内容哈希、原始 JSON、原始文件 | 不可变每日／临场快照 |
| `team_aliases` | 体彩名、标准名、英文名、provider、外部 ID、确认状态 | 跨数据源名称映射 |
| `match_features` | `as_of`、来源、特征 JSON、完整度、缺失项 | 时间截面赛前数据 |
| `predictions` | 三向概率、双方预期进球、比分分布、风险、模型版本、生成时间 | 追加式初版／临场预测 |
| `results` | 实际比分、赛果、录入时间、来源、复盘备注 | 赛后结果 |
| `model_versions` | 参数、训练区间、创建时间、回测结果 | 模型可复现性 |
| `match_review_queue` | 原因、候选、状态 | 无法唯一匹配时人工确认 |

旧 `matches` 表保留。迁移只复制可验证的对阵和赛果；旧预测缺少概率及预测时间，因此保留原表但不写入新版概率回测。

## 6. 输入数据约定

### 6.1 官方对阵

支持中文列名和英文列名，核心列为：`竞彩编号`、`比赛日期`、`联赛`、`主队`、`客队`（或 `对阵`）、`开赛时间`、`执行时区`、`让球`、`销售状态`、`比赛状态`、六项赔率、`原始数据来源`。

- 日期时间优先使用完整 `YYYY-MM-DD HH:MM`；只有 `MM-DD HH:MM` 时必须提供 `--date`。
-  naive 时间按 `执行时区`解释，数据库统一保存 UTC，同时保留原时区用于报告和跨日判断。
- 未识别字段不会用“当前时间”“主队”“客队”等伪值补齐。

### 6.2 球队映射

列为 `alias／体彩名称`、`standard_name／标准名称`、`english_name／英文名称`、`league`、`provider`、`external_id`、`review_status`。外部比赛自动匹配综合使用双方映射和两小时开赛时间容差，不只依赖中文名；非唯一候选进入人工队列。

### 6.3 赛前特征

可用 `fixture_key` 关联，也可用编号、双方和日期唯一关联。`as_of` 是防止未来数据泄漏的必填语义字段。支持：

- `expected_home_goals`、`expected_away_goals`：明确预期进球，优先级最高；
- `home_xg`、`home_xga`、`away_xg`、`away_xga`；
- `home_attack`、`home_defense`、`away_attack`、`away_defense`：相对联赛均值的乘数；
- `injuries`、`lineups`、`recent_form`、`h2h`、双方休息天数等文字或结构化依据；
- 其他字段可放入 `features_json`，原样保留用于后续模型扩展。

## 7. 模型口径

当前版本为 `poisson-dc-v1`。预期进球按以下优先级估计：

1. 明确输入双方预期进球；
2. 主队 `(home_xg + away_xga) / 2`，客队 `(away_xg + home_xga) / 2`；
3. 联赛均值 × 攻防乘数；
4. 仅有完整胜平负赔率时，去除水位后作赔率降级估计，并写入风险标记；
5. 无任何数据时使用联赛基线均值，完整度很低，不应输出强结论。

基础比分概率为：

```text
P(H=h, A=a) = Poisson(h; λ_home) × Poisson(a; λ_away)
```

对 `0:0`、`0:1`、`1:0`、`1:1` 使用 Dixon–Coles `rho` 修正，再在 `0..10` 球网格上归一化。三向概率由完整比分矩阵求和，比分报告取前 5 项。模型参数保存在 `model_versions`，预测保存输入截止时间，便于复现。

这是一套可运行基线，不宣称已完成分联赛参数训练。升班马、小样本、杯赛、伤停与阵容不确定信息应通过特征和风险标记体现；后续可在滚动窗口中拟合分联赛参数并新增模型版本。

## 8. 报告与回测

每日报告每场包含基本信息、当地开赛时间、数据完整度和来源、三向概率、双方预期进球、前 5 比分及概率、分析依据、风险提示、模型版本、预测时间、赛后比分与复盘字段。

回测只使用已落库且满足以下条件的记录：

```text
input_as_of <= predicted_at <= start_time_utc
```

指标包括 Log Loss、三分类 Brier 分数、胜平负准确率、首选／前三准确比分命中率、双方预期进球平均绝对误差，以及按预测概率分箱的实际频率。总体和分联赛分别统计。这里的回测是**已保存预测的滚动赛后评价**，不是使用未来赛果重新训练后再评价同一批比赛。

## 9. 自动任务与运行边界

- 测试工作流在代码变更时运行单元测试。
- `src/automation.py` 统一执行 Git 拉取、昨日赛果、今日对阵、预测、回测、中文摘要和推送；Kimi Claw 与 GitHub Actions 复用该入口。
- 每日工作流上传报告及数据库 artifact，并由自动化模块只提交 `data/football.db` 和 `reports/`。
- 抓取失败不会静默继续。无人值守环境若官方网页不稳定，应在仓库外准备好对阵文件后改用手动导入命令。
- API-Football 密钥只读环境变量，不写入数据库或文档；响应使用 15 分钟本地缓存。
- `sync-results` 只写入 FT／AET／PEN 且双方进球非空的赛果；未完结、无法唯一匹配或关联错误均不会生成伪赛果。
- API 适配器已实现但当前开发环境没有用户密钥，未进行真实账户额度和套餐字段验收；上线前需用小样本核对联赛覆盖、更新时间和请求量。

## 11. Kimi Claw 每日自动化

`scripts/daily_automation.sh` 是推荐 cron 入口，`python3 main.py daily` 是对应 Python 命令。执行顺序为：

```text
非并发锁与 Git 工作区检查
  → 可选 git pull --rebase
  → 初始化／迁移数据库
  → 文件或 API-Football 回填昨日赛果
  → 核对已有预测
  → 文件或公开网页导入今日官方对阵
  → 可选 API-Football 赛前特征
  → 生成预测、四格式报告、回测 JSON 和中文摘要
  → 仅暂存 data/football.db 与 reports/
  → commit 并可选 push
```

安全约束：

- 开始拉取或推送前要求工作区干净，避免覆盖人工修改。
- 文件锁防止 cron 重入；同日非 refresh 不重复生成同模型预测。
- 任何对阵或赛果关联错误都会中止后续推送；API 特征局部失败则保留警告并使用已有赛前数据。
- 不把 token、API key 或频道 secret 写入仓库、摘要和长期记忆；`git push` 使用已配置的凭证，不在命令参数中拼接 token。
- `DAILY_NO_GIT=1` 用于手动验收；先验证摘要和提交范围，再按 `CONTEXT.md` 配置非整点 cron。
- `reports/每日运行状态_日期.json` 供程序检查，`reports/每日中文摘要_日期.md` 供 Claw 推送聊天频道。
